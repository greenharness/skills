## Context

Cursor's `create-verification-skill` generates a project-local skill that
launches the app, drives it and collects proof, and is not done until it
has run once. Our F2 says "a piloted run (`run` skill)", which is generic:
no live checkout holds a `verify-*` skill, and start/seed/login facts sit
in free prose (social-planner `CLAUDE.md:105`, website-builder
`CLAUDE.md:124`, customer-vision `CLAUDE.md:79`, application-landscape
`author-e2e`). Every preview guide re-invents its sign-in.

We already beat Cursor on evidence and the F2 repair budget; the gap is
only the repo-local recipe. So: the generator, one F2 sentence, two
pilots, a measurement before widening.

## Goal

1. A `create-verify-skill` skill in `greenharness-skills` (workflow part).
   Run in a repo, it investigates (surface, run, drive, observe, isolate),
   writes `.claude/skills/verify-<app>/` with: Launch (readiness = usable,
   from an empty data dir), Doctor (one read-only check), Drive (stable
   handles), Evidence (files in the directory worktree-task F3 names,
   outside the worktree; action plus resulting state), Cleanup (kill only
   what it started, never by name),
   and `features/` for the top 3 to 5 features. It must execute the result
   once and list what it could not verify.
2. `worktree-task` F2 prefers the repo's `verify-*` skill, and falls back
   to today's Non-UI checks (no `run` skill ships in any part).
3. Two pilots and a measured decision.

## Non-goals

- A generic "skill generator framework". There is one instance; extract a
  shared contract only when a second generator exists (rule of three).
- A `--check` drift tool in v1 (decided in Phase 4 from pilot evidence).
- Replacing `author-e2e`/`heal-e2e` or `greenrack skill install`. The first
  gets folded into application-landscape's verify skill later; the second
  already solves drift for its output.
- Cursor's `maintain-verification-skill`: a stale step fails in F2 and is
  fixed in that PR.

## Design details

- The generator's frontmatter description triggers on "make the app
  verifiable", "write a verify skill", and on F2 finding no `verify-*`
  skill.
- A generated SKILL.md starts with a `generated-from:` list (the files the
  recipe was read from, with their blob hashes), so drift is detectable by
  hand now and by a tool later.
- Generic content only: `scripts/check.sh` forbids private hosts and home
  paths, so examples are placeholders.
- Evidence goes to the directory worktree-task F3 names (outside the
  worktree, never repo-relative, no literal home path). UI Drive says "hand
  this to `browser-check`"; each step needing a Green Harness part carries
  a fallback line for a checkout without it.
- Shell the skill writes, so one session cannot kill another's processes
  or stall: non-interactive (`CI=1 NO_COLOR=1`), output to a log; a free
  port, the listener inside our own process group (python
  `Popen(start_new_session=True)`: macOS has no `setsid(1)`), PGID in a pidfile, a deadline of 60 s
  or more; a `mktemp -d` data dir, its path in the pidfile; a `trap` on
  EXIT INT TERM covers launch-until-ready only and is cleared once ready
  (each tool call is a fresh shell); Cleanup is its own step:
  `kill -TERM -<pgid>`, then KILL, never by name, then the dir goes. Doctor prints
  `ok: …` or `fail: … — run <cmd>` (exit 0, 1, 2); a blocker names what,
  why and the next command. If two instances cannot run side by side, the
  skill declines to drive a shared one.
- The test (stdlib only, no PyYAML: CI runs bare `python3 -m unittest`)
  splits the frontmatter between the first two `---` lines on the first
  `: `, asserts `name` equals the directory name and `description` is
  non-empty, matches each of the five sections as a heading line
  (`^#{2,3} Launch\b`, re.M; not a substring), and matches the
  "execute once" rule as one exact sentence, plus one exact
  `verify-*`-preference sentence each in `worktree-task/SKILL.md` and
  `preview-guide-template.md` (same style as
  `tests/test_agent_model_fallback.py`).
- Rewording `worktree-task/SKILL.md` keeps the strings `model: "opus"` and
  `agent-model-fallback`, which `tests/test_agent_model_fallback.py` pins.
- Pilot baseline: from the session transcripts of each repo's last 5 plans
  (plans do not record F2 repairs), F2 repairs, blockers and wall time to
  the verdict, written here before Phase 2.
- Pilot success: a fresh session with no prior context completes one real
  F2 using only `verify-<app>`.
- Phase 4 widening order: application-landscape (folding `author-e2e`),
  social-planner, website-builder, customer-vision. A second generator
  triggers extracting the shared contract.

## Verification

- Generator: input = the skill run in a scratch repo; expected = a verify
  skill that launches, passes Doctor, drives one feature, leaves evidence
  outside the worktree (`git status` clean), and cleans up: a same-named
  decoy process survives, `pgrep -g <pgid>` is empty, a SIGINT mid-launch
  leaves no listener or data dir; Launch, Drive and Cleanup run as three
  separate tool calls and the app stays up until Cleanup. The result is recorded in the Phase 1
  PR body.
- Each pilot: input = the generated skill in a fresh session; expected =
  F2 completes without a repair; actual recorded per repo in the PR. A
  skipped precondition is a failure, not a pass.
- F2 wording: a plan in sre-agent run through worktree-task names the
  verify skill in its F2 record.
- Decision: widen if repairs per run are at most half the baseline or
  median F2 wall time is 30% or more lower, with 0 stale steps; build
  `--check` if 2 or more runs hit a stale `generated-from` step; drop if
  neither repairs nor wall time improved. A baseline of 0 repairs decides
  on wall time and blockers alone.
